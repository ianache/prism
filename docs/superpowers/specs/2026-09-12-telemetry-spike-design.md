# PRISM Telemetry Spike Design

**Status:** Approved design for specification work  
**Date:** 2026-09-12  
**Scope:** Telemetry-spike specification slice only

## 1. Purpose and scope

This design freezes the shape of the first PRISM specification artifact. It
does not implement a runtime, benchmark harness, broker integration, or
production workflow engine.

The artifact will specify the P0 telemetry benchmark in enough detail for
independent Rust, Java, and Go implementations to consume identical input,
produce logically equivalent output, and generate comparable measurements.
P1 transport is retained as a later benchmark phase. P2-P4 are future
compatibility concerns, not v1 implementation targets.

## 2. Design decisions

### 2.1 Canonical representation

- The benchmark input is a PRISM-owned synthetic binary frame.
- The frame uses a fixed, explicitly versioned layout.
- All multi-byte values are little-endian.
- Numeric values use integer or fixed-point representations with declared
  units; floating-point arithmetic is not part of the canonical correctness
  contract.
- Workflow, filter, data, and QoS contracts are canonical JSON documents
  validated with JSON Schema.
- Contracts are validated at control-plane/load time, not per filter
  invocation.

### 2.2 Execution model

The timed P0 path is:

```text
resident BinaryFrame
  -> F1 Validate
  -> F2 Decode
  -> F3 Normalize
  -> F4 Evaluate Rules
  -> F5 Classify
  -> F6 Route
  -> NormalizedTelemetry or Rejection
```

F1-F6 are deterministic, ordered transformations. A malformed frame stops at
F1 with a typed rejection. Unexpected runtime or filter faults remain
distinct execution failures.

The contracts define four linked concerns:

- **Workflow Contract:** identity/version, typed inputs and outputs, ordered
  nodes, and execution profile.
- **Filter Contract:** identity/version, typed input/output, declared errors,
  and capabilities.
- **Data Contract:** canonical types including `BinaryFrame`,
  `ValidatedFrame`, `NormalizedTelemetry`, and `Rejection`.
- **QoS Contract:** latency, throughput, memory, allocation, in-process, and
  observability requirements.

### 2.3 Canonical frame and workload

The frame specification will define exact field widths, units, ranges, and
checksum coverage. Its structure is:

```text
Header -> Core telemetry fields -> Bounded sensor/IO area -> Checksum
```

Core semantics include magic, version, flags, payload length, protocol,
device identifier, timestamp, position, speed, heading, ignition, battery,
and bounded sensor/IO data.

The dataset generator will produce deterministic approximately 100-, 250-,
and 500-byte payload classes from a recorded seed. Workload composition is
80% valid, 5% invalid, and 15% edge/complex. Invalid cases include
truncation, bad magic/version, length mismatch, range violations, unsupported
protocol, and checksum failure.

Expected outcomes are generated by an independent correctness oracle and
stored as fixtures. They compare logical values, not language-specific object
layouts or incidental metadata.

### 2.4 Filter semantics

- **F1 Validate:** checks framing, version, length, ranges, supported
  protocol, and checksum; emits `ValidatedFrame` or `Rejection`.
- **F2 Decode:** converts validated wire data into typed telemetry fields.
- **F3 Normalize:** applies canonical units, timestamp and coordinate
  normalization, and declared sensor defaults.
- **F4 Evaluate Rules:** applies a frozen, versioned deterministic rule set
  using integer/fixed-point comparisons.
- **F5 Classify:** maps rule results to a deterministic classification and
  severity.
- **F6 Route:** maps classification and context to a deterministic route enum;
  it performs no network or broker operation in P0.

The final output contract distinguishes successful telemetry, typed rejection
with stable error code and context, and unexpected execution failure.

## 3. Benchmark protocol

The specification defines four layers:

- **B0 Native:** direct equivalent functions without PRISM abstraction.
- **B1 Workflow:** PRISM contracts, registry, filter invocation, and the
  sequential pipeline.
- **B2 Observable:** B1 plus execution ID, per-filter timing, metrics, and
  tracing variants.
- **B3 Distributed:** producer/worker transport for P1 evaluation at
  workflow boundaries; brokers are not inserted between every filter.

Primary latency starts when a frame is resident and ready and ends when the
final success or rejection outcome is produced. Dataset I/O, process startup,
contract loading, result writing, and benchmark orchestration are excluded
from this primary timer and reported separately.

Every implementation consumes identical generated bytes and expected
results. The protocol requires warmed steady-state runs, one million frames
for sequential throughput, concurrency levels 1/2/4/8/16/32/64 where
meaningful, burst and sustained-load scenarios, all payload classes, and
complete hardware/runtime/compiler/OS metadata. Raw results are preserved;
reports are generated from raw data.

Workflow, observability, distribution, and serialization taxes are calculated
from matched runs. Tail latency, especially p99, is the primary comparison
metric; average latency is not a decision metric.

## 4. Acceptance gates

P0 initial gates are:

- p50 <= 250 microseconds;
- p95 <= 500 microseconds;
- p99 <= 1 millisecond;
- 100% logical correctness against the oracle;
- bounded memory with no sustained growth;
- no material latency degradation during sustained load;
- B1 p99 workflow tax <= 20% versus matched B0.

These are provisional hypotheses to be validated by the spike. The
specification will document threats to validity, including JIT warm-up,
garbage collection, CPU frequency variation, scheduler noise, timer
resolution, compiler optimization, and allocation behavior.

Correctness is a hard prerequisite: a runtime cannot qualify on performance
if its logical output differs from the oracle.

## 5. Required decision outputs

The completed spike specification will define evidence and report templates
for:

1. P0 runtime recommendation;
2. P0 data representation;
3. filter invocation strategy;
4. observability policy;
5. P1 transport recommendation or explicit deferral rationale;
6. execution-profile compatibility rules.

## 6. Deliberate boundaries and follow-up work

This design intentionally does not implement M1-M4, distributed durability,
agentic execution, a UI, Kubernetes deployment, or a complete workflow
orchestrator. The next specification task is to turn the approved semantics
into exact machine-readable schemas, byte offsets, fixed-point scales, rule
tables, error codes, and expected-output fixtures.

Before implementation, those details must be frozen and reviewed as the
benchmark gap/ambiguity report. No runtime implementation should begin until
the report is resolved.
